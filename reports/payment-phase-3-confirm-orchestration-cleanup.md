# Payment Refactoring - Phase 3

## 1. 변경 배경
이번 단계는 `PaymentUsecase.confirmSuccess()`의 오케스트레이션 구조를 정리하는 것을 목표로 했다.
이 메서드는 결제 승인 준비, PG 승인 요청, 응답 검증, 결제 조회 기반 재검증, 성공 확정, 실패 처리까지 결제 성공 콜백의 핵심 흐름을 한 곳에서 조합하는 진입점이다.

기능 자체는 이미 동작하고 있었지만, 메서드 내부에 여러 단계의 책임이 연속적으로 배치되어 있어 읽기 비용이 높고, 예외 처리까지 함께 섞여 있어 유지보수 관점에서 구조를 한 단계 더 정리할 필요가 있었다.

## 2. 기존 구조
기존 `confirmSuccess()`는 하나의 메서드 내부에서 아래 작업을 순차적으로 수행했다.
- 승인 준비 트랜잭션 실행
- PG 승인 요청
- 승인 응답 검증
- PG 결제 조회
- 조회 응답 재검증
- 성공 확정
- 예외 유형별 실패 처리

즉, 비즈니스 흐름 자체는 맞았지만 각 단계의 의도가 메서드 수준에서 분리되어 보이지 않았고, 코드 독해 시 어느 부분이 준비 단계인지, 어느 부분이 검증 단계인지, 어느 부분이 실패 처리 단계인지 빠르게 파악하기 어려운 구조였다.

## 3. 문제점
기존 구조의 문제를 정리하면 다음과 같다.
- **문제 1. 오케스트레이션 책임이 한 메서드에 과도하게 응집되어 있었다.**
  승인 준비부터 실패 처리까지 모든 단계가 하나의 메서드 안에서 처리되고 있었다.
- **문제 2. 단계별 의도가 코드에서 즉시 드러나지 않았다.**
  실제 결제 흐름은 분명히 여러 단계로 나뉘지만, 메서드 내부에서는 주석에 의존해 흐름을 읽어야 했다.
- **문제 3. 예외 처리 구조가 기능 단계와 섞여 있었다.**
  PG 응답 오류, 네트워크 오류, 내부 검증 실패가 모두 한 메서드 안에서 직접 처리되어 후속 변경 시 영향 범위 판단이 어려울 수 있었다.

## 4. 변경 내용
이번 단계에서는 `confirmSuccess()`의 흐름을 단계별 메서드로 분리해 오케스트레이션의 의도를 더 명확하게 드러내도록 정리했다.

주요 변경 내용은 다음과 같다.
- `prepareConfirm()` 추출
- `requestPaymentConfirmation()` 추출
- `verifyConfirmedPayment()` 추출
- `fetchConfirmedPayment()` 추출
- `verifyFetchedPayment()` 추출
- `finalizeConfirmedPayment()` 추출
- `handlePgResponseFailure()` 추출
- `handleVerificationFailure()` 추출
- 오케스트레이션 순서를 검증하는 테스트 추가
- 변경 전/후 동일 조건 벤치마크 추가

## 5. 변경 후 구조
변경 후 `confirmSuccess()`는 실제 결제 승인 흐름을 오케스트레이터처럼 읽을 수 있는 구조로 정리되었다.

변경 후 흐름은 다음과 같다.
1. `prepareConfirm()`
   - 승인 전 상태 준비
2. `requestPaymentConfirmation()`
   - PG 승인 요청 수행
3. `verifyConfirmedPayment()`
   - 승인 응답 검증
4. `fetchConfirmedPayment()`
   - PG 결제 정보 조회
5. `verifyFetchedPayment()`
   - 조회 응답 재검증
6. `finalizeConfirmedPayment()`
   - 성공 확정 및 응답 생성
7. `handlePgResponseFailure()` / `handleVerificationFailure()`
   - 예외 유형별 실패 처리

즉, 기존과 동일한 비즈니스 흐름을 유지하면서도 메서드 수준에서 단계가 더 명확하게 구분되는 구조로 바뀌었다.

## 6. 기대 효과
- **안정성**
  - 흐름이 더 분명해져 변경 시 실수 가능성이 줄어든다.
- **트랜잭션 분리**
  - 준비 / 승인 / 검증 / 확정 / 실패 처리의 역할 구분이 더 선명해진다.
- **테스트 용이성**
  - 오케스트레이션 순서와 예외 흐름을 더 직접적으로 검증할 수 있다.
- **확장성**
  - 이후 PG 연동 로직 추가, 검증 단계 확장, 예외 정책 세분화 시 메서드 단위 조정이 쉬워진다.

## 8. Before / After 비교
| 항목 | Before | After |
|---|---|---|
| confirmSuccess 구조 | 여러 단계가 하나의 메서드 내부에 연속 배치됨 | 단계별 메서드로 분리되어 오케스트레이션 의도 명확화 |
| 흐름 가독성 | 주석 의존도가 높음 | 메서드 이름만으로도 준비/요청/검증/확정/실패 처리 흐름 파악 가능 |
| 실패 처리 표현 | 기능 단계와 예외 처리 로직이 한 메서드에 섞여 있음 | PG 응답 실패와 검증 실패 처리를 별도 메서드로 분리 |
| 오케스트레이션 테스트 | 결과 중심 검증 위주 | 실행 순서와 예외 흐름까지 검증 가능 |
| 성능 기준선 | 구조 변경 전 수치 없음 | 변경 전/후 동일 조건 마이크로 벤치마크 비교 가능 |

## 9. 테스트 및 검증
이번 단계에서는 오케스트레이션 흐름 자체를 검증하는 데 집중했다.

### 단위 테스트
- `PaymentUsecaseTest`
- `PaymentUsecaseOrchestrationTest`
- `PaymentUsecaseBenchmarkTest`

### 검증 항목
- prepare -> PG 승인 -> 검증 -> PG 조회 -> 재검증 -> 성공 확정 순서 보장
- PG 응답 오류 시 실패 확정 및 예외 처리
- 네트워크 오류 시 pending 예외 처리
- 전체 백엔드 테스트 통과

## 10. 정량 지표
이번 단계의 정량 지표는 동일한 mocked 조건에서 `confirmSuccess()`를 반복 실행하는 마이크로 벤치마크를 기준으로 측정했다.
실제 PG/DB 부하가 아닌, 오케스트레이션 구조 변경 전후의 메서드 수행 비용 비교를 위한 기준선이다.

### 변경 전 테스트
- 반복 수: 5000
- 평균 응답 시간: 68.072µs
- p90: 108.900µs
- p95: 128.200µs
- 최대 응답 시간: 494.600µs
- 처리량: 13838.888 ops/s

### 변경 후 테스트
- 반복 수: 5000
- 평균 응답 시간: 67.315µs
- p90: 103.300µs
- p95: 124.000µs
- 최대 응답 시간: 630.600µs
- 처리량: 13966.274 ops/s

### 해석
구조를 메서드 단위로 분리했음에도 평균, p90, p95 지표는 기존과 유사하거나 소폭 개선된 수준을 유지했다.
즉, 가독성과 책임 분리 개선을 얻으면서도 오케스트레이션 수행 비용 증가는 사실상 없었다고 볼 수 있다.

## 11. 정리
이번 단계에서는 결제 승인 오케스트레이션의 핵심 진입점인 `confirmSuccess()`를 더 읽기 쉽고 유지보수하기 좋은 구조로 정리했다.
기능 자체를 바꾸기보다 승인 준비, PG 호출, 검증, 성공 확정, 실패 처리를 단계별 메서드로 분리해 의도를 더 명확하게 드러내는 방향으로 개선했다.

또한 변경 전/후 동일 조건 벤치마크를 통해 구조 개선이 성능 저하 없이 이루어졌음을 수치로 확인했다.
따라서 이번 단계는 **동일한 비즈니스 동작을 유지하면서, 결제 승인 오케스트레이션의 가독성과 변경 용이성을 높인 단계**라고 정리할 수 있다.
