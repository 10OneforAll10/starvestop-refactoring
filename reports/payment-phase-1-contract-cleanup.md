# Payment 리팩터링 Phase 1 - 결제 성공 콜백 계약 정리

## 프로젝트 개요
이번 단계는 결제 성공 콜백 구간에서 발생하던 용어 혼선과 응답 의미의 불명확성을 해소하는 데 초점을 맞췄다.
기존 구현에서는 외부 결제사에서 전달하는 `orderId`가 내부 시스템의 숫자형 주문 ID처럼 보였지만, 실제로는 결제 연동용 `orderKey` 역할을 하고 있었다.
또한 성공 콜백 응답이 단순 숫자 하나로 내려가고 있어 프론트엔드와 백엔드 간 계약이 충분히 설명적이지 않았다.

이 단계의 목표는 다음과 같았다.
- 결제 성공 콜백의 입력 의미를 명확히 정리한다.
- 성공 응답을 설명 가능한 구조로 바꾼다.
- 프론트엔드와 백엔드의 타입 계약을 일관되게 맞춘다.
- 변경 사항을 테스트와 정량 지표로 검증한다.

## 문제 정의
리팩터링 이전에는 다음과 같은 문제가 있었다.

- 외부 파라미터 이름은 `orderId`지만 내부 의미는 `orderKey`여서 혼동 가능성이 높았다.
- 성공 응답이 `Long` 하나만 반환되어 응답의 의미가 코드 바깥에서는 드러나지 않았다.
- 프론트엔드에서 `paymentType` 같은 불필요한 값을 함께 전달하고 있었다.
- 성공 페이지에서 변수명이 실제 의미를 충분히 반영하지 못했다.

이런 상태는 결제 흐름을 처음 읽는 사람에게 학습 비용을 높이고, 유지보수 과정에서 실수 가능성을 키운다.

## 해결 전략
이번 단계에서는 외부 API 계약을 불필요하게 깨지 않으면서도, 내부 코드의 의미를 더 분명하게 만드는 방향으로 정리했다.

핵심 접근은 아래와 같다.
- 외부 결제사가 보내는 쿼리 파라미터 이름은 유지한다.
- 내부 코드에서는 해당 값을 `orderKey` 의미로 해석한다.
- 성공 응답은 `orderId`, `orderKey`, `status`를 포함하는 명시적 DTO로 구조화한다.
- 프론트엔드도 같은 의미 체계를 공유하도록 타입과 호출부를 정리한다.

## 구현 내용
### 1. 성공 응답의 의미를 명시적 DTO로 개선
기존에는 성공 콜백 결과가 숫자 하나로만 반환되었다.
이번 단계에서는 아래 정보를 담는 응답 구조로 바꿨다.

- 내부 주문 식별자
- 외부 결제 연동 주문 키
- 승인 상태

이렇게 변경함으로써 응답만 보아도 어떤 값이 무엇을 의미하는지 즉시 이해할 수 있게 만들었다.

### 2. 입력 파라미터의 의미를 내부 코드에서 바로잡음
외부 결제사가 보내는 `orderId`는 실제로 내부 숫자형 PK가 아니라 결제 연동용 키였다.
이 때문에 컨트롤러와 유즈케이스 내부에서는 이를 `orderKey` 의미로 다루도록 정리했다.

이 방식은 다음 장점이 있다.
- 외부 결제사와의 호환성 유지
- 내부 코드 가독성 향상
- 도메인 의미와 구현 이름의 정합성 확보

### 3. 프론트엔드 타입 계약 단순화
프론트엔드에서는 성공 콜백 처리 로직을 더 명확하게 만들기 위해 호출 파라미터와 응답 타입을 정리했다.
불필요한 `paymentType` 전달을 제거했고, 응답도 숫자 하나가 아니라 의미 있는 구조체로 다루도록 수정했다.

### 4. 결제 성공 페이지 가독성 개선
성공 페이지에서는 결제 연동 키를 나타내는 값이 UUID처럼 오해될 수 있는 이름으로 관리되고 있었다.
이번 단계에서는 변수명을 실제 역할에 맞게 정리하고, 이후 주문 완료 페이지로 이동하는 흐름도 응답 계약에 맞춰 정돈했다.

## 테스트 전략
리팩터링은 동작 보존이 중요하기 때문에 변경과 동시에 테스트를 보강했다.
이번 단계에서는 다음 두 축으로 검증을 수행했다.

### 백엔드 단위 테스트
- 이미 성공한 결제 재진입 시 명시적 응답 DTO가 올바르게 반환되는지 검증
- 결제 승인 및 검증 성공 시 응답 구조가 기대값과 일치하는지 검증
- 성공 콜백 API가 응답 JSON에 필요한 필드를 모두 포함하는지 검증

### 프론트엔드 빌드 및 타입 검증
- 프로덕션 빌드를 통해 타입 정합성과 호출부 일관성을 확인

## k6 정량 검증
### 목적
이번 단계의 k6 테스트는 실제 결제 승인 비즈니스 부하를 측정하기 위한 목적이 아니라,
리팩터링된 성공 콜백 응답 계약이 안정적으로 직렬화되고 일관된 형태로 제공되는지를 수치로 확인하기 위한 계약 검증용 스모크 테스트다.

### 시나리오
- 초기 소규모 사용자 수에서 시작
- 점진적으로 동시 사용자를 늘림
- 짧은 지속 구간 동안 응답 일관성을 반복 검증
- 마지막에는 부하를 단계적으로 낮춤

### 결과
- 총 요청 수: 221
- 평균 응답 시간: 148.94µs
- p90: 643.8µs
- p95: 716.5µs
- 최대 응답 시간: 2.76ms
- 실패율: 0.00%
- 체크 성공률: 100.00%
- 평균 처리량: 5.51 req/s

### 해석
이번 단계의 수치는 실운영 환경 전체 성능을 대표하지는 않는다.
다만 결제 성공 콜백의 응답 계약 자체는 매우 가볍고 안정적으로 처리된다는 점을 확인할 수 있었다.
즉, 이번 리팩터링은 응답 구조 명확성과 타입 안정성을 높이면서도 기본적인 처리 비용을 거의 증가시키지 않았다.

## 성과 요약
이번 단계에서 얻은 실질적인 개선점은 다음과 같다.

- 결제 성공 콜백의 의미가 더 명확해졌다.
- `orderId`와 `orderKey`의 역할 구분이 분명해졌다.
- 프론트엔드와 백엔드가 공유하는 데이터 계약이 설명 가능해졌다.
- 이후 상태 전이 리팩터링과 실패 처리 정리에 들어가기 위한 기반이 마련되었다.
- 변경 사항을 테스트와 정량 지표로 함께 제시할 수 있게 되었다.

## 결론
이번 리팩터링은 단순한 네이밍 수정이 아니라, 결제 성공 콜백이 외부 입력과 내부 도메인 의미를 어떻게 연결하는지 명확히 재정의한 작업이었다.
또한 응답 구조를 self-descriptive 하게 바꾸고, 프론트엔드와 백엔드 모두에서 그 계약을 일관되게 사용하도록 정리했다.

포트폴리오 관점에서 이 단계는 다음 역량을 보여준다.
- 도메인 용어와 API 계약을 정리하는 능력
- 변경을 테스트로 보호하는 개발 습관
- 정량 지표를 함께 남기는 검증 중심 리팩터링 방식
- 프론트엔드와 백엔드를 함께 보는 통합적 개선 능력
