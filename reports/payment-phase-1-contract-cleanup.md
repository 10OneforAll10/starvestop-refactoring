# Payment Refactoring - Phase 1

## 1. 변경 배경
이번 단계에서는 결제 성공 콜백 구간에서 발생하던 용어 혼선과 응답 의미의 불명확성을 해소하는 것을 목표로 했다.
기존 구현에서는 외부 결제사가 전달하는 `orderId`가 내부 시스템의 숫자형 주문 ID처럼 보였지만, 실제로는 결제 연동용 `orderKey` 역할을 하고 있었다.
또한 성공 콜백 응답이 단순 숫자 하나로 내려가고 있어 프론트엔드와 백엔드 간 계약이 충분히 설명적이지 않았다.

이러한 상태는 결제 흐름 이해 비용을 높이고, 유지보수 과정에서 실수 가능성을 키우며, 프론트엔드와 백엔드의 타입 계약을 불안정하게 만드는 원인이 된다.

## 2. 기존 구조
기존 결제 성공 콜백 흐름은 외부 결제사로부터 `paymentKey`, `orderId`, `amount`를 전달받아 백엔드에서 승인 검증을 수행하는 구조였다.
그러나 실제 구현에서는 다음과 같은 특징이 있었다.

- 외부 쿼리 파라미터 이름은 `orderId`지만 내부 의미는 `orderKey`에 가까웠다.
- 성공 응답은 내부 주문 ID 하나만 반환했다.
- 프론트엔드에서는 성공 응답을 숫자값 중심으로 해석하고 있었고, 응답 구조 자체의 의미는 코드상에 충분히 드러나지 않았다.
- 호출 파라미터 중 실제 사용되지 않는 값도 함께 전달되고 있었다.

즉, 동작은 가능했지만 계약의 의미가 코드 전반에서 일관되게 표현되지는 않는 구조였다.

## 3. 문제점
기존 구조의 문제를 정리하면 다음과 같다.
- **문제 1. `orderId`와 `orderKey`의 의미가 혼재되어 있었다.**
  외부 API 파라미터 이름과 내부 도메인 의미가 일치하지 않아 혼동 가능성이 높았다.
- **문제 2. 성공 응답이 self-descriptive 하지 않았다.**
  응답이 숫자 하나로만 구성되어 있어 어떤 값인지 응답 자체로는 충분히 설명되지 않았다.
- **문제 3. 프론트엔드와 백엔드 계약이 느슨했다.**
  사용하지 않는 파라미터가 함께 전달되고 있었고, 성공 페이지 로직도 실제 의미를 충분히 반영하지 못했다.

## 4. 변경 내용
이번 단계에서는 결제 성공 콜백 계약을 명확하게 정리하는 데 집중했다.

주요 변경 내용은 다음과 같다.
- 성공 응답을 명시적 DTO로 변경
  - `orderId`
  - `orderKey`
  - `status`
- 컨트롤러 내부에서 외부 `orderId` 파라미터를 `orderKey` 의미로 해석하도록 정리
- 프론트엔드 `confirmPayment()` 호출 타입 정리
- 사용하지 않는 `paymentType` 제거
- 성공 페이지에서 변수명과 응답 처리 방식 정리
- 결제 성공 콜백 API 및 유즈케이스 테스트 보강

## 5. 변경 후 구조
변경 후 구조는 외부 API 계약은 유지하면서 내부 의미를 더 분명하게 드러내는 방향으로 정리되었다.

변경 후 흐름은 다음과 같다.
1. **외부 성공 콜백 수신**
   - `paymentKey`, `orderId`, `amount` 수신
2. **내부 의미 정리**
   - 외부 `orderId`를 내부에서는 `orderKey` 의미로 사용
3. **결제 승인 및 검증 수행**
   - 결제 승인 로직 실행
4. **명시적 성공 응답 반환**
   - `orderId`, `orderKey`, `status`를 포함한 DTO 반환
5. **프론트엔드 후속 처리**
   - 응답 DTO를 기반으로 주문 완료 페이지 이동

즉, 단순한 숫자 반환 구조에서 의미가 드러나는 응답 계약 구조로 바뀌었다.

## 6. 기대 효과
- **안정성**
  - 프론트엔드와 백엔드 간 계약 해석 오류 가능성이 줄어든다.
- **트랜잭션 분리**
  - 성공 콜백 처리의 입력 의미와 반환 의미가 더 분명해진다.
- **테스트 용이성**
  - 응답 계약 자체를 테스트로 검증할 수 있다.
- **확장성**
  - 이후 성공 응답에 추가 필드가 필요해질 때 구조적으로 확장하기 쉽다.

## 8. Before / After 비교
| 항목 | Before | After |
|---|---|---|
| 외부 `orderId` 해석 | 내부 의미가 코드상 명확히 드러나지 않음 | 내부에서는 `orderKey` 의미로 명확하게 해석 |
| 성공 응답 형태 | 숫자형 ID 하나 반환 | `orderId`, `orderKey`, `status`를 포함한 명시적 DTO 반환 |
| 프론트 호출 계약 | 불필요한 파라미터 포함, 의미가 느슨함 | 필요한 값만 전달하고 타입 계약 명확화 |
| 성공 페이지 로직 | 응답 의미가 코드상 충분히 드러나지 않음 | 응답 DTO 기준으로 후속 처리 수행 |
| 테스트 보호 수준 | 성공 계약 검증 범위가 제한적임 | 유즈케이스 + 컨트롤러 테스트로 계약 검증 |

## 10. 정량 지표
이번 단계의 k6는 실제 결제 승인 비즈니스 부하 측정이 아니라, 성공 콜백 응답 계약이 안정적으로 직렬화되고 일관된 형태로 제공되는지를 검증하기 위한 계약 스모크 벤치마크로 사용했다.

### 변경 전 테스트
- 정량 측정 미수행
- 성공 콜백 응답 계약에 대한 별도 k6 기준선 부재

### 변경 후 테스트
- 총 요청 수: 221
- 평균 응답 시간: 148.94µs
- p90: 643.8µs
- p95: 716.5µs
- 최대 응답 시간: 2.76ms
- 실패율: 0.00%
- 체크 성공률: 100.00%
- 평균 처리량: 5.51 req/s

### 해석
변경 전에는 성공 콜백 응답 계약에 대한 정량 기준선이 존재하지 않았다.
변경 후에는 응답 계약 자체를 독립적으로 측정 가능한 상태가 되었고, 매우 낮은 응답 비용으로 안정적으로 처리됨을 확인할 수 있었다.

## 11. 정리
이번 단계에서는 결제 성공 콜백에서 발생하던 용어 혼선과 응답 의미의 불명확성을 정리했다.
외부 API 파라미터 이름은 유지하면서도 내부에서는 `orderKey` 의미를 명확하게 반영하도록 구조를 다듬었고, 성공 응답을 명시적 DTO로 변경해 계약 자체가 더 설명 가능해졌다.

또한 프론트엔드와 백엔드가 공유하는 타입 계약을 정리하고, 이를 테스트와 정량 지표로 검증함으로써 이후 상태 전이와 실패 처리 리팩터링으로 넘어가기 위한 기반을 마련했다.
