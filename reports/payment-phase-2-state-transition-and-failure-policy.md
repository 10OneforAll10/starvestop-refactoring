# Payment 리팩터링 Phase 2 - 상태 전이 및 실패 처리 정책 정리

## 프로젝트 개요
이번 단계는 결제 처리에서 가장 민감한 구간인 상태 전이와 실패 처리 정책을 검증하고 보강하는 작업에 집중했다.
결제 도메인에서는 성공보다 실패 경로가 더 중요할 때가 많다. 특히 재시도 가능한 실패와 재시도 불가능한 실패를 구분하고, 그에 따라 재고 복구 여부가 달라지는 구조에서는 작은 상태 전이 오류도 실제 운영 리스크로 이어질 수 있다.

이번 단계의 목적은 다음과 같았다.
- 결제 준비, 성공 확정, 실패 확정 흐름의 상태 전이를 테스트로 명확히 검증한다.
- retryable / non-retryable 실패 분기를 수치와 코드로 확인한다.
- 금액 불일치 처리처럼 초기 상태에서 바로 실패해야 하는 케이스의 버그를 수정한다.
- 상태 전이 결과를 정량 지표와 함께 문서화한다.

## 문제 정의
1단계에서 API 계약을 정리한 뒤 코드를 다시 점검하면서, 상태 전이 관점에서 중요한 위험 지점이 확인되었다.

가장 핵심적인 문제는 다음과 같았다.
- 금액 불일치가 발생하면 결제는 즉시 non-retryable 실패가 되어야 한다.
- 하지만 기존 엔티티 규칙에서는 `FAILED_NON_RETRYABLE` 전이가 `PENDING` 상태에서만 허용되어 있었다.
- 실제 prepare 단계의 금액 불일치 검사는 `REQUESTED` 상태에서 발생할 수 있기 때문에, 이 경우 예외가 발생하며 실패 확정이 정상적으로 처리되지 않을 수 있었다.

즉, 실패를 처리해야 하는 코드가 오히려 상태 전이 규칙 때문에 실패하는 구조적 문제가 숨어 있었다.

## 해결 전략
이번 단계에서는 상태 전이 규칙을 무작정 크게 바꾸기보다, 테스트를 먼저 작성해 현재 동작을 드러내고 실제로 잘못된 전이 규칙만 최소 범위로 수정하는 방식으로 진행했다.

핵심 원칙은 다음과 같다.
- prepare, success finalize, fail finalize를 각각 별도 테스트 대상으로 본다.
- 성공 경로만이 아니라 중복 승인, 금액 불일치, retryable 실패, non-retryable 실패를 모두 명시적으로 검증한다.
- 재고 복구 여부를 상태와 함께 검증한다.
- 실제 코드 수정은 테스트가 실패한 지점을 해결하는 최소 단위로 제한한다.

## 구현 내용
### 1. PrepareConfirmTx 테스트 보강
결제 준비 단계에 대해 다음 상황을 검증했다.
- 이미 주문이 결제 완료된 경우 추가 승인 없이 종료되는지
- 금액이 일치하면 `PENDING` 상태로 전이되는지
- 금액이 다르면 즉시 실패 처리되는지
- 이미 `PENDING`이면 중복 승인 요청을 막는지

이 테스트를 통해 prepare 단계가 결제 승인 직전의 게이트 역할을 올바르게 수행하는지 확인했다.

### 2. FinalizeSuccessTx 테스트 보강
성공 확정 단계에 대해 다음을 검증했다.
- 이미 결제가 완료된 경우 중복 확정 없이 안전하게 종료되는지
- `PENDING` 상태에서는 결제 성공과 주문 완료가 함께 확정되는지

이 테스트는 중복 콜백이나 재진입 상황에서도 성공 확정 로직이 과도하게 다시 실행되지 않음을 보여준다.

### 3. FinalizeFailTx 테스트 보강
실패 확정 단계에 대해 다음 시나리오를 검증했다.
- 5xx 응답은 retryable 실패로 분류되는지
- retryable 실패에서는 재고를 복구하지 않는지
- 비재시도성 실패에서는 non-retryable로 전이되는지
- non-retryable 실패에서는 재고가 복구되는지
- 금액 불일치가 `REQUESTED` 상태에서도 즉시 실패로 확정되는지

### 4. 실제 버그 수정
테스트 수행 과정에서 금액 불일치 케이스가 실제로 실패했다.
원인은 `failNonRetryable()`가 `PENDING` 상태만 허용하고 있었기 때문이다.

이를 아래 방향으로 수정했다.
- `FAILED_NON_RETRYABLE` 전이를 `REQUESTED`, `PENDING` 두 상태에서 허용

이 변경은 prepare 단계에서 금액 검증 실패가 발생했을 때 도메인 규칙과 실제 비즈니스 요구가 일치하도록 맞춘 것이다.

## 테스트 전략
이번 단계는 전부 상태 기반 테스트로 설계했다.
핵심은 특정 메서드가 호출됐는지보다, 호출 이후 결제 상태와 재고 복구 정책이 기대한 결과로 귀결되는지를 보는 것이었다.

검증 축은 다음과 같다.

- 이벤트 릴레이 호출 여부
- 재고 복구 여부
- 중복 처리 방지 여부
- 실패 분류의 정확성

## k6 정량 검증
### 목적
이번 단계의 k6는 서비스 레이어 메서드를 직접 부하 테스트하는 방식이 아니라,
상태 전이 결과를 표현하는 응답 계약을 모사한 시나리오를 통해 success / retryable failure / non-retryable failure 분기 구조가 일관된 형태로 처리되는지를 측정하는 스모크 벤치마크로 사용했다.

즉, 이 수치는 실제 DB 트랜잭션 성능 측정값이 아니라 상태 전이 정책을 외부 응답 형태로 표현했을 때의 처리 일관성과 경량성을 보여주는 기준선이다.

### 시나리오
- success 상태 표현
- retryable failure 상태 표현
- non-retryable failure 상태 표현
- 세 가지 상태를 혼합해 점진적으로 부하 증가
- 최대 동시 사용자 수 12 기준으로 실행

### 결과
- 총 요청 수: 254
- 평균 응답 시간: 311.53µs
- p90: 729.65µs
- p95: 869.56µs
- 최대 응답 시간: 3.61ms
- 실패율: 0.00%
- 체크 성공률: 100.00%
- 평균 처리량: 6.34 req/s
- 최대 VU: 12

### 해석
이번 벤치마크에서는 세 가지 대표 상태 시나리오를 혼합해도 응답 계약 수준에서는 매우 안정적으로 처리되었다.
특히 non-retryable 실패에서 `stockReleased=true`가 일관되게 유지되고, success 및 retryable 실패에서는 재고가 유지되는 구조를 정량 검증할 수 있었다.

## 성과 요약
이번 단계에서 얻은 개선은 다음과 같다.
- 결제 준비, 성공 확정, 실패 확정 흐름이 테스트로 보호되기 시작했다.
- retryable / non-retryable 실패 정책이 더 명확해졌다.
- 금액 불일치의 실제 상태 전이 버그를 수정했다.
- 재고 복구 정책을 코드와 테스트 모두에서 확인할 수 있게 되었다.
- 다음 단계에서 confirm 오케스트레이션을 더 안전하게 정리할 기반이 마련되었다.

## 결론
이번 단계는 결제 도메인에서 가장 위험한 구간 중 하나인 실패 처리와 상태 전이를 테스트 기반으로 고정하는 작업이었다.
특히 금액 불일치가 발생한 초기 상태에서 실패 확정이 정상적으로 이루어지지 않던 문제를 발견하고 수정함으로써, 상태 머신의 신뢰성을 한 단계 끌어올렸다.
