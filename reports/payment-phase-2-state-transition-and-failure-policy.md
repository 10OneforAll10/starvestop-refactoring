# Payment Refactoring - Phase 2

## 1. 변경 배경
이번 단계에서는 결제 처리 과정에서 가장 민감한 구간인 상태 전이와 실패 처리 정책을 검증하고 보강하는 것을 목표로 했다.
기존 구조에서는 결제 준비, 성공 확정, 실패 확정의 역할 분리는 어느 정도 이루어져 있었지만, 실제 실패 케이스가 어떤 상태에서 어떤 방식으로 처리되는지 명확하게 보장되는 수준은 아니었다.

특히 금액 불일치, 재시도 가능 실패, 재시도 불가능 실패와 같은 예외 흐름은 운영 환경에서 직접적인 결제 안정성과 연결되기 때문에, 이 단계에서는 실패 경로를 명확하게 검증하고 상태 전이 규칙을 비즈니스 요구에 맞게 정리하는 것이 필요했다.

## 2. 기존 구조
기존 결제 흐름은 크게 결제 준비, 결제 성공 확정, 결제 실패 확정으로 구분되어 있었다.
주요 로직은 `PrepareConfirmTx`, `FinalizeSuccessTx`, `FinalizeFailTx`에 분리되어 있었고, 상태 전이 자체는 `Payment` 엔티티 내부 메서드가 담당하는 구조였다.

흐름 관점에서 보면 다음과 같은 구조였다.
- `PrepareConfirmTx`
  - 결제 승인 전 주문 상태 및 금액 확인
  - 승인 진행 가능 여부 확인
- `FinalizeSuccessTx`
  - 결제 성공 상태 확정
  - 주문 상태를 `PAID`로 변경
- `FinalizeFailTx`
  - 예외 유형에 따라 실패 상태 확정
  - 필요 시 재고 복구 수행
- `Payment`
  - 상태 전이 규칙 보유
  - 상태 변경 시 이벤트 생성

전체적인 책임 분리는 존재했지만, 특정 실패 케이스가 실제로 어떤 상태에서 어떤 결과로 이어지는지 파악하려면 여러 클래스를 함께 읽어야 했고, 실패 처리 정책이 테스트로 충분히 고정되어 있지 않은 상태였다.

## 3. 문제점
기존 구조의 문제를 정리하면 다음과 같다.
- **문제 1. 상태 전이 규칙과 실제 비즈니스 요구가 완전히 일치하지 않았다.**
  금액 불일치와 같은 실패는 결제 준비 단계에서 즉시 non-retryable 실패로 처리되어야 하지만, 일부 상태 전이 규칙은 특정 상태에서만 실패 확정을 허용하고 있었다.
- **문제 2. 실패 처리 정책이 테스트로 충분히 보호되지 않았다.**
  retryable / non-retryable 실패 구분, 재고 복구 여부, 중복 처리 방지와 같은 핵심 정책이 코드에 존재해도 이를 보장하는 테스트가 부족했다.
- **문제 3. 전체 흐름 관점에서 추적 비용이 높았다.**
  결제 준비, 성공 확정, 실패 확정이 분리되어 있었지만 실제 결제 1건의 상태 전이를 이해하려면 여러 클래스를 함께 읽어야 했고, 실패 경로는 특히 이해 비용이 높았다.

## 4. 변경 내용
이번 단계에서는 상태 전이 검증과 실패 정책 검증을 강화하는 데 초점을 맞췄다.

주요 변경 내용은 다음과 같다.
- `PrepareConfirmTx` 테스트 추가
  - 이미 완료된 주문 처리
  - 정상 금액 승인 준비
  - 금액 불일치 즉시 실패 처리
  - 중복 승인 차단
- `FinalizeSuccessTx` 테스트 추가
  - 중복 성공 확정 방지
  - `PENDING` 상태에서 성공 확정
- `FinalizeFailTx` 테스트 추가
  - retryable 실패 분기
  - non-retryable 실패 분기
  - 재고 복구 여부 검증
  - 금액 불일치 즉시 실패 확정 검증
- `Payment.failNonRetryable()` 상태 전이 규칙 수정
  - 기존 `PENDING` 전용 허용에서
  - `REQUESTED`, `PENDING` 허용으로 변경
- 상태 전이 정책을 정량 검증하기 위한 k6 시나리오 추가

## 5. 변경 후 구조
변경 후 구조는 기존의 역할 분리를 유지하면서, 각 트랜잭션 단계의 책임과 검증 범위를 더 명확하게 만드는 방향으로 정리되었다.

변경 후 흐름은 다음과 같다.
1. **결제 준비**
   - 주문 상태와 결제 상태 확인
   - 금액 검증
   - 정상일 경우 `REQUESTED -> PENDING`
   - 금액 불일치 시 즉시 실패 처리
2. **결제 성공 확정**
   - 이미 성공된 요청인지 확인
   - `PENDING -> SUCCEEDED`
   - 주문 상태를 `PAID`로 변경
3. **결제 실패 확정**
   - 예외 유형에 따라 retryable / non-retryable 분기
   - retryable 실패는 재고 유지
   - non-retryable 실패는 재고 복구
4. **결제 엔티티**
   - 상태 전이 규칙을 직접 관리
   - 허용 가능한 상태 전이만 수행

즉, 구조 자체를 크게 변경한 것은 아니지만, 각 단계가 어떤 상태를 받아 어떤 상태로 전이시키는지가 테스트와 코드 양쪽에서 더 분명하게 드러나는 구조가 되었다.

## 6. 기대 효과
- **안정성**
  - 실패 경로와 상태 전이 규칙이 테스트로 보호되어 예외 상황에서의 오류 가능성이 줄어든다.
- **트랜잭션 분리**
  - 결제 준비, 성공 확정, 실패 확정의 책임 구분이 더 명확해진다.
- **테스트 용이성**
  - 각 단계가 독립 테스트 대상으로 분리되어 검증이 쉬워진다.
- **확장성**
  - 이후 PG 예외 유형 추가, 실패 정책 변경, 상태 전이 규칙 보강 시 단계별 확장이 쉬워진다.

## 8. Before / After 비교
| 항목 | Before | After |
|---|---|---|
| 금액 불일치 실패 처리 | `REQUESTED` 상태에서 즉시 non-retryable 실패 확정이 보장되지 않음 | `REQUESTED` 상태에서도 즉시 `FAILED_NON_RETRYABLE` 전이 가능 |
| 실패 처리 검증 수준 | 실패 정책이 코드에만 존재하고 독립 테스트가 부족함 | prepare / success / fail 단계별 테스트로 정책 고정 |
| retryable / non-retryable 구분 | 구조는 있었지만 테스트로 충분히 보장되지 않음 | 예외 유형, 상태 전이, 재고 복구 여부까지 검증 |
| 재고 복구 정책 | non-retryable 실패 시 재고 복구 정책이 명시적으로 검증되지 않음 | 재고 복구 여부를 테스트와 정량 시나리오에서 함께 확인 |
| 상태 전이 가시성 | 흐름을 이해하려면 여러 클래스를 함께 추적해야 함 | 단계별 테스트를 통해 전이 규칙이 더 분명하게 드러남 |

## 10. 정량 지표
이번 단계의 k6는 실제 DB 트랜잭션 부하 측정이 아니라, 상태 전이 결과를 외부 응답 형태로 표현했을 때 success / retryable failure / non-retryable failure 구조가 일관되게 유지되는지를 확인하기 위한 스모크 벤치마크로 사용했다.

### 변경 전 테스트
- 상태 전이 정책에 대한 정량 시나리오 부재
- success / retryable / non-retryable 분기 구조를 수치로 비교할 기준선 없음

### 변경 후 테스트
- 총 요청 수: 254
- 평균 응답 시간: 311.53µs
- p90: 729.65µs
- p95: 869.56µs
- 최대 응답 시간: 3.61ms
- 실패율: 0.00%
- 체크 성공률: 100.00%
- 평균 처리량: 6.34 req/s
- 최대 VU: 12

### 해석
변경 전에는 상태 전이 정책을 외부에서 재현 가능한 형태로 검증하는 정량 기준이 존재하지 않았다.
변경 후에는 success / retryable / non-retryable 실패 구조를 분리된 시나리오로 확인할 수 있게 되었고, 상태 정책이 일관된 응답 구조로 안정적으로 유지됨을 검증했다.

## 11. 정리
이번 단계에서는 결제 상태 전이와 실패 처리 정책을 중심으로 구조를 검증하고 보강했다.
기존에는 성공 경로보다 실패 경로와 예외 상황에서의 동작이 상대적으로 명확하게 보장되지 않았고, 일부 상태 전이 규칙은 실제 비즈니스 요구와 완전히 일치하지 않는 문제가 있었다.

이번 리팩터링을 통해 결제 준비, 성공 확정, 실패 확정의 각 단계가 어떤 상태를 기준으로 동작하며 어떤 결과로 이어지는지를 테스트로 명확하게 검증할 수 있게 되었다.
특히 금액 불일치와 같은 즉시 실패 케이스에서 non-retryable 실패가 정상적으로 확정되도록 상태 전이 규칙을 수정함으로써, 실패 처리 신뢰성을 높였다.

또한 retryable 실패와 non-retryable 실패를 구분하고, 재고 복구 여부까지 함께 검증함으로써 결제 도메인의 핵심 정책이 코드와 테스트 양쪽에서 더 분명해졌다.
이로 인해 이후 결제 승인 오케스트레이션 정리, 예외 처리 정책 세분화, 외부 PG 연동 확장과 같은 다음 단계 작업도 더 안정적으로 진행할 수 있는 기반이 마련되었다.

즉, 이번 단계는 단순한 테스트 추가를 넘어서 **결제 상태 머신의 동작을 명확하게 정의하고, 실패 경로를 안전하게 고정한 단계**라고 정리할 수 있다.
